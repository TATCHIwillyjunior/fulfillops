# ADR-001: PostgreSQL transactions and a durable worker table

- **Status:** Accepted
- **Decision date:** 2026-11-14

## Context

Order acceptance must reserve inventory and persist asynchronous work atomically.
Clients may retry requests, multiple API replicas may receive the same key at
once, and workers may restart while processing. An in-memory queue or inventory
counter would lose authoritative state on restart and cannot coordinate
replicas.

## Decision

Use PostgreSQL as the shared durable store and use `worker_jobs` as a
transactional work table. Accept an order in one database transaction:

1. Acquire a PostgreSQL transaction advisory lock derived from the
   `Idempotency-Key`.
2. Read the unique idempotency mapping and compare a canonical payload hash.
3. Lock product rows in sorted SKU order and verify all requested quantities.
4. Decrement inventory and insert the order, aggregated order lines, and job.
5. Commit before returning the acceptance receipt.

Workers claim eligible jobs with `FOR UPDATE SKIP LOCKED`, store an expiring
lease, and retry failures with bounded exponential backoff. Exhausted jobs are
retained in a dead-letter state. Completing a job writes a unique
`fulfillment_receipts` row and marks both job and order completed in one
transaction.

## Consequences

- Inventory and job creation are atomic without a separate message broker.
- Unique constraints plus transaction locks protect same-key replay across API
  replicas; row locks protect different-key inventory competition.
- Delivery is at least once. The unique receipt and transactional completion
  make the lab's persisted fulfillment effect idempotent.
- PostgreSQL is a shared dependency and queue polling adds database load.
- `fulfillment_receipts` models a local business-side effect only. If shipping,
  payment or another external system is added, it must receive an idempotency
  key or use an outbox/consumer deduplication pattern.

## Alternatives considered

- **Process-local queue or mutex:** rejected because it cannot survive process
  restart or coordinate API/worker replicas.
- **Redis Streams:** viable, but adds an additional service and coordination
  boundary. It is not needed for this project's durable-work volume.
- **PostgreSQL plus a separate queue:** rejected for the current scope because
  it introduces a dual-write problem unless an outbox is added; the work table
  already provides durable claiming and recovery.
